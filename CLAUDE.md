# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Solaryn's Expedition: a World of Warcraft addon (Lua 5.1, no build step) for **WoW: Forever**, which is in beta (`_classic_beta_` client, interface 16001). It does quest routing, "what next" suggestions and explored-zone tracking. Slash commands: `/sol` or `/expedition`.

This directory is the source of truth. The live client folder is only a copy that `deploy.sh` writes.

## Commands

All commands run from the repo root. The tests `require` via `./?.lua;./test/?.lua` and open `SolarynExpedition.toc` by relative path.

```bash
lua5.1 test/harness.lua            # full test suite (mock WoW API); prints "N passed, M failed", exits non-zero on failure
lua5.1 test/check_load_order.lua   # loads files in TOC order and checks each file's ns.* prerequisites
lua5.1 test/load_addon.lua         # loads the addon and shows what got built, without Init's pcall hiding errors
luac5.1 -p <file>.lua              # syntax check one file
./deploy.sh                        # syntax check + tests + load order, then copy *.lua, *.xml and the TOC to the live client
                                   # (WOW_ADDON_DIR overrides the destination)
./deploy.sh --force                # copy without running any checks
```

There is no way to run a single test. `harness.lua` is one script with `check(label, cond, detail)` assertions grouped under `== section ==` headers, so run the whole thing and grep the output. After deploying, run `/reload` in game.

## Slash commands

`Slash.HELP` in `Core_Slash.lua` is the single reference for every `/sol` command (summary, details, example); `/sol help [command]` prints it. When you add or rename a command, update `HELP` and the README's command tables, because tests fail if `COMMANDS`, `HELP` and `README.md` disagree.

## Architecture

**Load order is defined by `SolarynExpedition.toc`** and it matters. `Init.lua` creates the namespace. `Core_Constants` must load before `Core_Util` (which reads `ns.Defaults`), and `Core_Explored` before `Core_Suggest`. When you add a file, add it to the TOC. If it depends on other modules, add an entry to `REQUIREMENTS` in `test/check_load_order.lua`.

**Namespace.** Every file starts with `local ADDON_NAME = ...` and `local ns = _G.SolarynExpedition`. The client passes each file only the addon name as a vararg, not the private addon table, and the test loaders deliberately do the same. Don't change them to pass `ns` as a second argument: that once hid a nil-namespace crash that only showed up in game. `Init.lua` also assigns the global `ns` (it has no `local`), and the test scripts use that global.

**Events and modules (`Init.lua`).** There is one dispatcher frame. `ns:RegisterEvent(event, fn, owner)` adds a handler, and `ns:Fire(event, ...)` calls the handlers for an event, each inside a pcall. An ALL_CAPS name is a client event and is also registered on the dispatcher frame. If the client rejects the name, the error is stored in `ns.badEvents` instead of being thrown. Custom events use lowercase names and never touch the frame: `route_changed`, `suggestions_updated`, `explored_changed`, `waypoint_set`. There's no client event for the world map opening or the minimap resizing, so those use `HookScript("OnShow"/"OnSizeChanged")`. Frequent events such as `QUEST_LOG_UPDATE` go through `ns:Debounce(key, delay, fn)` (`C_Timer.After`; it runs immediately when `C_Timer` is missing) so that a burst causes one rescan. Pass an `owner` to `ns:UnregisterEvent`, because leaving it out removes every module's handlers for that event. A module calls `ns:RegisterModule(name, mod)` to get `Initialize` (on ADDON_LOADED, after SavedVariables are set up) and `OnLogin` (on PLAYER_LOGIN). If a module fails to initialize, the error is stored in `mod.initError` and reported with `ns:Error`.

**Data flow.**
- `Core_QuestData` is the only file that talks to `C_QuestLog`. It turns quests into normalized entries. Objectives and locations are cached per *generation*. The generation goes up on every quest-log or zone event, and `QuestData` registers its handlers first so later modules always read fresh data. For locations, `Waypoints()` asks every source the client has and keeps the most specific answer. The sources, best first: `GetQuestsOnMap` (the markers the world map draws, which also covers the hand-in point of a finished quest), `GetNextWaypoint`, `GetQuestUiMapID`, `C_TaskQuest`, and last `GetNextWaypointForMap`. That last one only answers when the objective is on *another* map, so it can't be the main source. `/sol where` shows in game what each source returns. Coordinates are the client's 0–1 map fractions everywhere, in saved data and in the mock alike. Multiply by 100 only when showing them to a person.
- `Core_Overrides` holds hand-recorded objective and turn-in positions in `SolarynDB.overrides`, plus quest chain links (`ns.Chains`). The data comes from the client first, and overrides are applied on top.
- `Core_ZoneData` builds the zone list by walking `C_Map.GetMapChildrenInfo` from Cosmic (946), Azeroth (947), and every map above the player. Classic-era clients may lack the Cosmic root. `Get()` falls back to `GetMapInfo` for any map the walk missed. Maps are classified by `Enum.UIMapType`. It also provides zone level ranges and progression. `LevelRange()` uses `C_Map.GetMapLevels` when the client has it, otherwise the `CLASSIC_ZONES` table, which is keyed by zone *name* so it survives map renumbering and never applies to unknown zones. `LevelStatus()` rates a zone as ok, late, high or low for your level. `Progression()` recommends zones on your continent that fit your level and aren't the other faction's home zones: ones you're already in range for first, nearest first. The panel's location strip and Zones tab use it, and the Next tab suggests a zone only when your current one is outgrown or too high.
- `Core_Explored` estimates zone coverage by sampling the player's position on an N×N grid, stored in `SolarynCharDB.zones`. It samples on the containing zone (`WorldAncestor`), so being in a town sub-map still counts. It uses no per-zone data files. It also imports the client's fog of war. `ImportFromClient` asks `C_MapExplorationInfo.GetExploredAreaIDsAtPosition` about each grid cell's centre, storing the results in `rec.revealed` and the discovered area IDs in `rec.areas`. It runs for every zone at login and for the current zone on any zone-change event, and is recomputed from scratch each time. Coverage is the union of walked and revealed cells over the full grid. The fog of war never says how much of a map *can* be discovered, so the zone's **"Explore <Zone>" achievement** takes priority when there is one. Its criteria are the zone's real list of areas, so coverage = areas found ÷ criteria, and an achievement earned by this character means 100%. The achievement is found by scanning `GetCategoryList` for names matching `^Explore (.+)$`, with `KNOWN_EXPLORE_IDS` as a name-checked fallback. A snapshot, including the missing area names, is stored in `rec.achievement` and refreshed on `CRITERIA_UPDATE` and `ACHIEVEMENT_EARNED`. Without an achievement, coverage is the grid estimate, which reads below 100% even for a fully explored zone.
- `Core_Route` orders stops by nearest neighbour (`Route.OrderStops`), stored in `SolarynCharDB.route`. With `batchTurnIns` (the default), a hand-in's distance is weighted ×3 unless it's within 75 yards, so the route finishes nearby objectives before walking back to hand in. Building and re-planning share this ordering. It also holds the **guide**. The route state has `current` (the stop being headed to), `guiding`, and `visited` (keys from `Route.StopKey` for stops already reached). By default (`advanceWhenDone`), a stop is finished by finishing its quest work. On a quest event, `PromoteTurnIns` swaps a now-complete quest's remaining objective stops for its hand-in stop and `Replan`s the unvisited part of the route from the player's position, and a hand-in stop is done once the quest leaves the log; then `Advance` moves the waypoint on. With `advanceWhenDone` off, a 0.5s ticker also advances on arrival within `arriveRadius`. Changed defaults that are already saved in people's settings are migrated once in `Init.lua` (`db.settingsVersion`). A rebuild while guiding moves `visited` stops to the front and resumes after them, because opening the panel rebuilds a stale route.
- `Core_Suggest` ranks four kinds of suggestion (`turnout`, `objective`, `unlock`, `explore`) using a weighted score. The weights are the `w*` keys in `ns.Defaults.settings`, and the options sliders edit them directly. With `sortByDistance` (the default), the Next tab is ordered nearest quest first: pinned quests, then located quests, then quests with no location, then zone suggestions. The weights only decide the order when it's off.
- `Core_MapPins` handles waypoints and world-map pins. Pins use Blizzard's map canvas API: a provider built with `CreateFromMixins(MapCanvasDataProviderMixin)` is added to `WorldMapFrame` once and refreshed on `route_changed`. It asks for pins with `AcquirePin("SolarynExpeditionRoutePinTemplate", ...)`, and that template is defined in `SolarynExpedition.xml`, whose `OnLoad` mixes in the pin behaviour. Pins must **not** set `OnEnter`/`OnLeave`/`OnMouseUp` scripts. The canvas asserts on that and wires those scripts itself, calling the pin's `OnMouseEnter`, `OnMouseLeave` and `OnClick` methods; just `EnableMouse(true)` and define the methods. `WorldMapFrame:SetMapPoint` doesn't exist; to open a map, use `OpenAt`, which calls `OpenWorldMap` or `SetMapID`. The mock's map canvas calls `OnAdded` on providers and only builds templates it finds in the XML, so the same misuse fails in tests.
- The `UI_*` files (Panel with Next/Route/Zones tabs, Options, Minimap, HUD) rebuild in response to the custom events above. `UI_HUD.lua` is the on-screen route tracker. It's visible while guiding, or always with `hudAlways`. It rebuilds on events and refreshes distance and the arrow every 0.2s. The arrow's angle is `atan2(-dx, -dy) - GetPlayerFacing()` in map space (map x points east and y south; facing is 0 at north and increases counter-clockwise), so it only shows a direction when the player and the stop are on the same map.
- **Quest item buttons** (`UI_HUD.lua`): `SecureActionButtonTemplate` buttons named `SolarynExpeditionQuestItemButton1..3`. They're parented to `UIParent`, not the tracker, so the tracker never becomes protected, and they're placed by screen coordinates. Their attributes, visibility and position only change outside combat; during combat `HUD:UpdateItems` sets `itemsPending` and `PLAYER_REGEN_ENABLED` applies it. `QuestData:QuestItem` finds the item from `GetQuestLogSpecialItemInfo`, then from bag items the client ties to the quest, then from usable quest items named in the objectives. `Bindings.xml` declares the "Use quest item" binding; the client loads it automatically, so it's not listed in the TOC.
- **Quest givers** (`Core_QuestGivers.lua`): the client only reveals what an NPC offers when you talk to it, so this learns from `GOSSIP_SHOW`, `QUEST_GREETING`, `QUEST_DETAIL`, `QUEST_PROGRESS`/`QUEST_COMPLETE` and `QUEST_ACCEPTED`. It stores `SolarynDB.npcs[npcID]` (offers, takes, where you stood) and `SolarynDB.questGivers[questID]`, account-wide. NPC IDs come from the creature GUID (`IDFromGUID`). NPC tooltips list what's still available and what the NPC takes back. `QuestData:TurnInLocation` falls back to the NPC seen taking the quest, else the giver (`approximate`), when the client has no turn-in marker.
- **Quest tooltips** (`UI_Tooltip.lua`): unit and world-object tooltips get quest lines when the name appears in an objective (`NameMatches` handles common plurals). It uses `TooltipDataProcessor` post-calls when the client has them, otherwise `OnTooltipSetUnit`/`OnShow` hooks. It skips quests the tooltip already shows, and falls back to `C_QuestLog.UnitIsRelatedToActiveQuest`.

**Settings.** Add new settings to `ns.Defaults.settings` in `Core_Constants.lua`. Always read them through `ns.Settings()`, which fills in missing defaults so keys added after a user's SavedVariables were written never come back as nil. SavedVariables are `SolarynDB` (account-wide: settings, overrides, character index) and `SolarynCharDB` (per character: zones, route, stats, suggestOverrides).

## API constraints (Forever beta)

- The API is still changing. Probe optional APIs in `CAPS` in `Core_Util.lua`, check `ns.Has.<cap>` before using one, and degrade gracefully instead of erroring. `ns.Try`, `ns.SafeNum` and `ns.SafeStr` guard against missing APIs and "secret" values.
- `C_Map.GetAllMapInfo` and `C_QuestLog.GetActiveQuestMapIDs` **do not exist** on this client, and the test suite asserts that the addon doesn't depend on them. (The header comment in `Core_ZoneData.lua` still mentions `GetAllMapInfo`, but the code walks the map tree instead.)
- **Secret values:** in combat, notably in groups, unit names and tooltip text can arrive as secret values. Addons may hold them, but comparing (even `== nil`), concatenating, indexing or string-processing one is an error. Check `ns.IsSafe(v)` (which calls `issecretvalue` first) **before** touching anything that came from a unit or a tooltip, and use the unit token ("mouseover"), never the name, to decide whether a unit exists. Tooltip hooks are additionally wrapped in `pcall`. The mock's `Mock.secret(v)` simulates these values (`type()` still reports the underlying type), but plain Lua can't trap comparing one against a literal, so guard first.
- Position APIs return inconsistent shapes (Vector2DMixin, a plain `{x,y}` table, or a bare pair of numbers). Always go through `ns:VecXY`.
- Map coordinates are 0–1 fractions, as the client returns them, in the code, in overrides and in the mock. Mixing in 0–100 coordinates once made every exploration sample land in the same grid cell.

## UI conventions

- Windows come from `Widgets:Window` (`UI_Widgets.lua`), which provides the shared flat chrome, a draggable title bar that moves the frame (never the bar itself), Escape-to-close, and saving and restoring its position. Positions are saved as `{ v = 2, point, relPoint, x, y }`; saves without `v = 2` are ignored.
- Only Textures can take a colour or image fill. Use `Widgets:Fill` to make one. Calling `SetColorTexture` or `SetTexture` on a Frame errors in game, and the mock now errors too.
- Panel rows are pooled per kind (`suggestion`/`route`/`zone`) and filled in on each render. Don't create frames inside render functions.
- `Panel:Refresh` catches render errors so they can't break the addon, and records them in `Panel.lastError`. Tests assert that field is nil.
- The minimap button is built like a LibDBIcon button (a gold `MiniMap-TrackingBorder` ring). Its position is only an angle, `settings.minimapPos`. Dragging recomputes that angle from the cursor with an `OnUpdate` script, so the button stays on the ring; don't use `StartMoving` for it.

## Test environment

`test/mockenv.lua` is a hand-written mock of only the widget and `C_Map`/`C_QuestLog` functions the addon calls. It has four zones (1 Elwynn, 2 Westfall, 3 Durotar, 84 a dungeon; all with parent 100) laid out on exact 1000-unit squares so distance assertions can use real numbers, and a five-quest log (IDs 1001–1005). If new code calls a client API the mock doesn't implement, add it to `mockenv.lua`. The mock is deliberately strict where the client is: secure frames (template containing "Secure") raise `ADDON_ACTION_BLOCKED` on `SetAttribute`, `Show`, `Hide` or `SetPoint` while `Mock.inCombat` is true; `RegisterEvent` errors for names not in `M.KNOWN_EVENTS`, so when you use a new real client event, add it to that list. The harness triggers events with `ns:Fire`, and a separate section checks that every client event with a handler is registered on `ns.dispatcher`.
